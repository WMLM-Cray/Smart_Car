# spica:闭环赛道 + 双输出,在真实几何上

spica 是这套路段策略架构的名字。它合并 v1 和 v2 的长处。

**2026-09-28 确定的设计目标：**

- 可变速度能不能用在第一圈？——即「直线跑最高速度，雷达识别到弯就降到该弯所需
  的上限速度，出弯再调回去」。
- 地图生成器在**闭环**前提下把赛道做复杂（各种角），以贴近真实赛道。

**所以 spica 的训练赛道 = 闭环规则赛道(和真实赛道同构),复杂度在闭环前提下加。**
开放路段(L1–L4、L6)不再是主训练场。

**再纠正一个流传的说法。** 常被引用的是「v1 阶梯在各自速度上碾压 v2」。
这个结论是在 `rc` 分支的旧仿真器上得出的,而 main 的评估器上从来没有并列跑过。
在 main 上并列跑了,结论**反过来了**:

| 级别 | R_min p10 | m4 (v1) 干净率 | m4 净空 p10 | candidate_167 (v2) 干净率 | v2 净空 p10 |
|---|---|---|---|---|---|
| L3 | 0.614 | 0.625 | −0.002 | 0.925 | +0.105 |
| L4 | 0.637 | **0.400** | −0.002 | **1.000** | +0.106 |
| L5 | 0.812 | **0.400** | −0.004 | **0.975** | +0.136 |
| L6 | 0.699 | **0.400** | −0.005 | **1.000** | +0.149 |

（同种子基 71000000,n=40,cap 钉在各自训练速度,m4=1.0、rung1=1.2。）

m4 的净空 p10 是**负的** —— 它撞上去了。v1 的记录值 0.913/0.987 是在 `rc` 的
旧仿真器(`fastsim/env.py` + `ConeTrackEnv`)和旧赛道族上测的,与 main 不可比。
**两套评估仪器不可比**这条教训在这里第一次真的咬到了人。

## 一、v1 的墙是**曲率地板**,不是速度

v1 的训练赛道只有圆弧和直道,要让它适配更复杂的赛道环境,得先知道它到底卡在哪。
**数据完全支持「卡在几何」这一条,而且比预想的更干净。**

### 1.1 先做证伪实验(最便宜、决定方案前提的那个)

方案初稿担心:万一 v1 在 L1/L2 上也塌了,说明是车辆参数或观测口径在 main 上变了,
整个"复杂度"的解释就站不住。**实测排除了这个可能:**

```
m4 (candidate_002) 在 main 的 fastsim 上,cap 钉 1.0,n=40,种子基 71000000
  L1  干净率 1.000   净空 p10 +0.314
  L2  干净率 0.925   净空 p10 +0.140
  L3  干净率 0.625   净空 p10 −0.002
  L4  干净率 0.400   净空 p10 −0.002
  L5  干净率 0.400   净空 p10 −0.004
  L6  干净率 0.400   净空 p10 −0.005
```

L1/L2 是满分,**所以车辆参数和观测口径都没变**。塌陷精确地从 L3 开始。

### 1.2 机制:v1 训练时的曲率地板是 1.0 m

v1 的训练赛道族在 `rc` 分支上只有两个来源:

| 文件 | 赛道形态 | 曲率地板 |
|---|---|---|
| `fastsim/track.py` | 光滑随机环形(三个余弦谐波扰动半径) | `TrackParams.min_curvature_radius = 1.6` |
| `fastsim/track_rules.py` | 规则赛道:直道 + 45/90/135° 圆弧弯 | `RuleTrackParams.bend_radius_min = 1.0` |

**只有圆弧和直道,中心线处处光滑,而且最紧的弯半径也有 1.0 m。**

我实测了 main 每一级赛道中心线**低于这个地板 1.0 m 的长度占比**(n=30,同种子基):

| 级别 | R_min 中位 | p10 | 低于 1.0m 占比 | m4 干净率 |
|---|---|---|---|---|
| L1 | 2.287 | 2.079 | **0%** | 1.000 |
| L2 | 1.494 | 1.203 | **0%** | 0.925 |
| L3 | 1.071 | 0.645 | 40% | 0.625 |
| L4 | 1.081 | 0.605 | 40% | 0.400 |
| L5 | 0.909 | 0.811 | 73% | 0.400 |
| L6 | 0.790 | 0.700 | 100% | 0.400 |

**单调对应,而且 L1/L2 的 0% 解释了为什么只有它们满分。**
m4 在 L4/L5/L6 上的净空 p10 是**负的** —— 它不是保守地停下,是撞上去
(collision 11~15 / 40)。

### 1.3 但曲率地板不是唯一的轴

**L5 是个关键反例,它推翻了"尖角才是难点"的简单说法。** 查 `LEVELS` 配置:

```
L5:  sharp_chance=0.0  jog_chance=0.0  taper_chance=0.0  gap_chance=0.0  loop=True
L1:  sharp_chance=0.0  jog_chance=0.0  taper_chance=0.0  gap_chance=0.0  loop=False
```

**L5 和 L1 的特征开关完全相同,只是 `loop=True`** —— 它是 `generate_loop` 造的
**闭环规则赛道,同样只有圆弧和直道**。它的塌陷纯粹来自 `bend_radius_min` 被压到
`max(width/2, bend-0.25) ≈ 0.9`,即**曲率地板被压到 1.0 以下**。

而 L3 和 L4 的"低于地板占比"**都是 40%**,干净率却是 0.625 vs 0.400。
差别在 L4 多了 `gap_chance=0.2`(无边界段)和 `one_side_none_chance=0.1`。
失败形态也印证:L3 全是 collision(15/15),L4 起才出现 off_track。

**所以有两个轴:曲率地板(主)+ 边界信息缺失(次)。** 见 §1.5。

### 1.4 由此确定的 spica 第一目标

> **把策略的曲率地板从 1.0 m 压到车的物理极限 0.83 m 附近,
> 同时在边界信息缺失的路段上不失去可通行性。**

不是"跑得更快"。速度是第二位的,而且 v2 的速度天花板本来就只有 1.0(§3.3)。

### 1.5 0.400 的巧合已排查:不是同一批种子

L4/L5/L6 的干净率**精确都是 0.400 = 16/40**,我怀疑是"同一批 16 个种子在每一级
都容易"。**按种子逐一核对后,怀疑不成立:**

```
L4∩L5∩L6 = {8, 17, 18}                    3 条
并集(三级里至少成功过一级)                34 条不同种子
三级全败                                  6 条 {11,19,23,25,30,36}
```

独立假设下期望重叠 `40 × 0.4³ = 2.56` 条,实测 3 条 —— **与独立完全吻合**。
所以三级的 16 条成功赛道是**三批不同的赛道**,`n=40` 的置信度没有被高估。

作为对照,v2 在同一批种子上的成绩是 L4 **40/40**、L5 **39/40**、L6 **40/40** ——
**不是"好一点",是几乎不留任何失败**。这个差距不是调参能补的,是训练分布的问题。

### 1.6 老师上界:老师自己在六级上全是 40/40

**这是决定方案生死的一条。** 如果老师自己都过不去复杂赛道,DAgger 就没有可学的
标签,整个 spica 方案是死的。实测(同种子基,n=40,真实车辆参数):

| 级别 | 老师干净率 | 净空 p10 | 重规划失败次数 |
|---|---|---|---|
| L1 | **1.000** | +0.146 | 1 |
| L2 | **1.000** | +0.139 | 1 |
| L3 | **1.000** | +0.136 | 71 |
| L4 | **1.000** | +0.138 | 8 |
| L5 | **1.000** | +0.139 | **1235** |
| L6 | **1.000** | +0.127 | 2 |

**结论:标签在每一级都存在,而且老师的净空 p10 稳定在 +0.13 左右 —— 不比在
L1 上更勉强。** 学生(m4)在 L4/L5/L6 上是 0.400 且净空为负,老师在同一批赛道上
是 1.000 且净空 +0.14。**这中间的差距 100% 是学生没有泛化到这些几何,
不是赛道不可通、不是老师不会。**

L5 的重规划失败 1235 次(每局平均 31 次)值得单独留意:老师每拍重规划,在闭环
紧弯上经常解不出路线,于是**沿用旧路线**。它照样 40/40,说明沿用是安全的;
但这意味着 L5 上有相当比例的标签来自"过期的规划"。**学生学的是这些标签,
所以 L5 的难度里有一部分是标签质量问题,不只是几何。**

## 二、为什么 v2 在复杂赛道上强这么多

三个原因,都能在代码里指出来:

**1. 老师会规划速度,而且规划得保守得多。**

```python
# training/road_teacher.py
A_LAT = 0.30    # 老师过弯的横向加速度上限(模块默认,与历史行为逐位一致)
# 放开要走 plan(..., a_lat=) / road_train --a-lat / 评估脚本 --a-lat
```

而车的物理极限是 `a_lat_max = 7.85 m/s²`(0.8g)。**老师的 0.30 比车的能力保守 26 倍。**
R=1.0m 的弯,老师限到 `sqrt(0.30/1.0) = 0.55 m/s`。v1 的老师
(`fastsim/planner.py` 的 `SpeedPlanTeacher`)用的也是 `a_lat_max * margin = 7.85 * 0.85 = 6.67`,
即 R=1.0m 限到 2.58 m/s —— 比 v2 的老师激进 4.7 倍。

**2. v2 的老师每拍重规划,不跟中心线。**

`Teacher.__call__` 里 `REPLAN_EVERY = 1`,每拍都从**车当前位姿**重规划前方 8m 的
最小曲率路线。v1 的老师跟的是**固定的中心线**(`preview.py` 的 `pure_pursuit`)。
在尖角处,中心线本身是贴着尖角走的,而最小曲率路线会外-内-外切进去 ——
后者才是车能走的。

**3. v2 的训练环境带三层可通性筛选。**

`training/road_check.py` 的 `check()` 要求:老师能在路面内规划出 R≥0.95 的路线、
沿路线摆车身净空 ≥0.08、每 0.5m 至少一侧 10m 内有回波、老师用这局的真实车辆参数
真开一遍且净空 ≥0.05。**任何一层不过就重抽路和参数。** v1 的 `curriculum.py`
只有赛后的 `passed()` 判据,没有事前筛选。

## 三、spica 的架构

### 3.1 v1 可以无损热启动到 v2 —— 这是合并的接口

我实测验证了:两个观测是**同一套通道,v2 多一个**。

```
v1 (52维): [48扇区, speed/scale, target_speed/scale, yaw_rate/3, last_steer]
v2 (53维): [48扇区, speed/1.5,   cap/1.5,            yaw_rate/3, last_action[0], last_action[1]]
```

用同一组输入喂两个 `observe()`,前 52 维 `np.array_equal` 为 **True**,逐位差 **0.0**。
展平缓冲是帧主序,所以 260 维 → 265 维是**精确的列重排**:每帧 52 列插到 53 列块的前 52 位,
新通道权重置 0。

**我把重排代码真跑了一遍**(m4 = `candidate_002`,300 组随机输入,**含 History 滚动**,
用 `common/road_policy.py` 的 `forward` 和 v1 的 `SteeringPolicy` 逐拍对比):

```
转向输出最大差 = 0.000e+00
```

不是"1e-07 量级",是**逐位相同**。列重排是纯排列,浮点上完全无损。

**结论:v1 模型能无损灌进 spica。** 现在做不到不是架构不兼容,是两道硬闸:
`training/road_train.py` 的 `--init` 要求 `schema == 'road_v2'`,
`common/road_policy.py` 的 `RoadPolicy.__init__` 同样。

顺带一个发现:**v1 的老师本来就会规划速度,只是被丢掉了。**
`fastsim/planner.py` 返回 `[v_target/v_cmd_fwd, steer/max_steer]`,而训练里只取了
`teacher(None, env)[1]` —— 转向。**两边的老师都出速度,两边的观测本来就对齐,
只是 v1 那边把它扔了。**

### 3.1b 速度通道:既会跟 cap,也确实会看弯 —— 两个检验

**要回答的问题:可变速度到底能不能用在第一圈?** 常见的顾虑是「第一圈为了实时性
要固定速度」。**先纠正这个前提:「为了实时性固定速度」在代码里没有依据** ——
全仓库搜 `实时` 零命中。速度是常数是因为训练时 `cap` 通道被随机化,
模型学成"跟着 cap 走";v1 那边更直接,动作只有一维转向,速度是命令行常数。
`RoadEnv.step` 的动作**一直**是 `[转向, 速度]` 两维,实时变速从来不是架构限制。

那速度通道到底学到了什么?两个检验:

**检验 A —— 同一条赛道,只改 `cap`,速度指令跟着变吗?**

```
L3-0  cap 0.50 -> 0.495   cap 0.75 -> 0.751   cap 1.00 -> 0.932   跟随 YES
L5-0  cap 0.50 -> 0.498   cap 0.75 -> 0.747   cap 1.00 -> 0.927   跟随 YES
(8/8 条赛道全部 YES)
```

跨局汇总 `corr(速度指令, cap) = +0.990`。**策略确实在跟 cap。**

**检验 B —— cap 钉死 1.0,速度指令还随"前方最紧的弯"变吗?**

```
合并 corr(速度指令, 前方 3m 内最紧弯半径) = +0.404
合并单圈速度跨度 中位 = 0.408 m/s
```

**显著正相关。弯越紧(R 越小)速度越低 —— 这正是物理上正确的方向。**

**结论:速度通道既会跟 cap(主),也确实在为弯道减速(次)。** 它是真的学到了
一点速度规划,不是纯粹的 cap 复读机。

### 3.1c 但在第一圈,这个可变速度买不到任何东西

关键数字:**每一级最紧的弯,物理上允许多快**(车的抓地 0.8g = 7.85 m/s²):

| 级别 | 最紧弯 R_min | 老师限速 | **物理限速** | vs 策略上限 1.0 |
|---|---|---|---|---|
| L1 | 1.447 | 0.455 | **2.33** | 2.3x |
| L2 | 1.072 | 0.529 | **2.71** | 2.7x |
| L3 | 0.529 | 0.753 | **3.85** | 3.9x |
| L4 | 0.553 | 0.737 | **3.77** | 3.8x |
| L5 | 0.765 | 0.626 | **3.20** | 3.2x |
| L6 | 0.674 | 0.667 | **3.41** | 3.4x |

**最紧的弯也允许 2.3 m/s 以上,而策略的动作上限只有 1.0 m/s。**
所以在当前速度区间里,**第一圈不存在"必须减速才能过弯"的时刻** ——
全程恒定 1.0 m/s 也能过每一个弯。

而老师(`A_LAT=0.30`)规划出的速度谱是 0.47~0.99,**同一圈内跨度 0.4~0.5 m/s**。
这个减速是**老师自己保守出来的**(它的横向加速度假设比车真实能力保守 26 倍),
不是物理需求。

**所以:可变速度现在就在跑,但它在第一圈是"空转"的 —— 减速降到的速度,
仍然远高于过弯真正需要的速度。** 速度只有在**突破 1.0 之后**才买得到东西,
那时候"哪里该减速"才第一次成为真问题。

**对 spica 的含义:§六 的"第二步解锁速度"不是可选项,它是让速度通道
从"空转"变成"有用"的唯一途径。** 在 1.0 以内继续调速度通道是白费力气。

### 3.1d 「直线全速、见弯降档」可行 —— 而且雷达量程刚好够到 3.0

**「直线全速、见弯降档」可行 —— 而且雷达量程刚好够到 3.0。**
约束不在控制律,在刹车距离。

刹车距离 `d = (v² − v_corner²) / (2a)`,弯内限速取老师口径 0.562 m/s:

| 直道目标速度 | 需刹车距离(实测滑行 0.73) | 雷达 10m |
|---|---|---|
| 1.0 | 0.47 m | OK |
| 2.0 | 2.52 m | OK |
| 2.5 | 4.06 m | OK |
| **3.0** | **5.95 m** | **OK** |
| 3.5 | 8.17 m | OK |

**10 m 雷达支持的直道最高速度:按实测滑行 0.73 → 3.86 m/s;
按老师计划减速 0.45 → 3.05 m/s。**

**这是一个漂亮的巧合:阶梯顶档 3.0 m/s 正好卡在雷达量程支持的边界上。**
也就是说"直线全速、见弯降档"这套方案,**在阶梯已有的全部速度档位上都成立**,
不需要更远的雷达。超过 ~3.0 才需要改雷达或改减速策略。

**但注意"检测到弯"这件事本身**:10 m 外雷达看到的锥桶,在闭环赛道上**同时包含
折回来的其它路段**(`generate_loop` 的注释专门讲过这件事,它正是把 v2 在赛道 A 上
干扰掉的原因)。所以"看到弯"不等于"我的路前面有弯" —— **识别必须能区分
"前方本路的弯"和"旁边别的路段"**。这是 §七 的风险 7。

### 3.1e 闭环赛道生成器:复杂度定在「有价值但不过激」

**设计约束:闭环前提下把赛道做复杂(各种角),但要「有价值、别太复杂」,
且「别拿真实赛道过拟合」。**

**所以定配置的准则不是「尽量难」,也不是「对齐 A–D 的曲率」**,而是:

> **覆盖 v1 没见过、但车能过的那条带。**

v1 的曲率地板是 1.0 m,车的转弯极限是 0.83 m —— **有价值的区间就是 `[0.83, 1.0)`**,
即「v1 从没练过、但车完全过得去」的几何。低于 0.83 的是车勉强能过的,
占比太高就是浪费训练预算;拿 A–D 去反推生成参数则是换了个马甲的过拟合。

按这个准则重新探参(n=25,种子基 83000000,经过 `road_check` 三层筛选):

| 配置 | R_min 中位 | 赛道 R_min<1.0 占比 | 赛道 R_min<0.83 占比 | 老师出圈 |
|---|---|---|---|---|
| A 现状 L5 | 0.929 | 80% | 24% | 25/25 |
| **C 中紧 `loop_bend=(0.9,1.2)`** | **0.916** | **92%** | **28%** | **25/25** |
| D 中紧+窄 `width=(1.35,1.5)` | 0.879 | 84% | 28% | 25/25 |
| F 上一版(窄+最紧+尖端) | 0.780 | 100% | **80%** | 25/25 |

**定 C。** 理由:
- 把「探到 v1 地板以下」的赛道从 80% 提到 **92%**,覆盖了想覆盖的那条带;
- 只有 **28%** 的赛道低于车极限 0.83 —— 大多数几何是车从容能过的,不是勉强能过;
- **不动路宽**(保持 1.4~1.6)。窄是**另一个失效轴**(guard 的距离阈值 vs 半宽),
  混进来几何结论就没法归因;
- 老师 25/25 出圈,标签存在。

**否掉上一版的 F**:80% 的赛道低于车极限,大部分是「车勉强能过」的几何,
不是想教给策略的东西 —— 这正是「别太复杂」这条设计约束。

两条硬边界(试出来的,别再撞):

1. **`s_bends_min=3` 全失败。** 增加 S 弯组数会让布局在 16.8m 场地内闭不上环
   (`_solve` 解出的主直道超出 `[6.0,12.5]`)。**闭环的复杂度只能从"弯更紧 / 路更窄 /
   端部更尖"来,不能从"元素更多"来。** 这是规则赛道尺寸的结构性约束。
2. **`loop_bend` 下限被 `max(width/2, bend−0.25)` 托住。** 想更紧必须同时降
   `loop_width`,否则下限被半宽顶住不起作用。

**落地:`simulation/fastsim/road.py` 的 `LEVELS` 里加**

```python
Level('L5c', loop=True, loop_bend=(0.9, 1.2)),
```

(加在末尾,不动已有各级在断点里的下标。)

### 3.1f 闭环生成器只暴露了三个旋钮,形状空间其实是锁死的(**2026-09-29 订正**)

**「闭环地图的元素是不是太少了,不都长一样吗」——查完确认这个判断是对的,
而且比想象的更严重。**

`generate_loop` 原来只暴露 `width` / `bend` / 桶距三个量,其余形状参数**全部锁在
`RuleTrackParams()` 的默认值上**:

```python
p = _replace(RuleTrackParams(), width=width, bend_radius_min=..., bend_radius_max=1.8,
             n_boards=5, end_radius=...)
#   square_end_chance / right_angle_ratio / s_bends_* / height_* / main_straight_*  <- 没传,吃默认
```

**后果:不管抽多少种子,闭环永远是同一个"长条形矩形回路"家族。**
把 24 条 L5c 的中心线叠在一张图上,形状肉眼几乎重合。之前所有"多跑几条赛道"
的多样性主张,在几何层面是站不住的。

**修复:在 `Level` 上加 8 个 `loop_*` 旋钮,`None` = 老行为逐位不变。**

```python
loop_height      # 主直道到回程直道的间距(赛道"厚度")
loop_square_end  # 端部做成方角(两个直角)的概率
loop_right_angle # 回程折角里直角的比例,其余抽 45°/135°
loop_s_bends     # 回程台阶组数(每组 2 个镜像对 = 4 个弯)
loop_main        # 主直道长度(闭合解出来,超范围重抽)
loop_bend_max    # S 弯半径上限
loop_turn_angles # 折角可选角度
```

**回归验证:所有旋钮都传 `None` 时,同种子生成的中心线和锥桶逐位不变。**
这是这条改动的底线 —— 不这么做,已有的 L5c 训练结果就没法比了。

**新家族的实测形状**(每条 30 条赛道,同种子基):

| 家族 | 设定 | R_min 中位 | 长宽比 | 采样失败率 |
|---|---|---|---|---|
| `L5c` | 老默认(对照) | 0.883 | 2.12 | 0% |
| `L5ra` | 全直角 + 方角端部 + 高度拉大 | 0.862 | 2.23 | **49%** |
| `L5rd` | 无方角 + 只抽 45/135° | 0.918 | **2.80** | 0% |
| `L5sq` | 短主直道 + 大高度 | 见下 | 见下 | 见下 |

**`L5ms`(台阶密集,`s_bends=4~5`)已证明不可用:闭合成功率 0%。**
独立测量 `s_bends` 的闭合率:2→0.29、3→0.00、4→0.00、5→0.00。
**规则赛道的复杂度只能从"弯更紧"来,不能从"元素更多"来** —— 这是 §3.1e 那条
结构性约束的第二次确认。

**`L5ra` 有 49% 的赛道抽不出来**(`_solve` 解不出闭合的主直道),`sample_episode`
200 次尝试后抛 `RuntimeError`。它在 mix 里的实际效果是:25% 的名义配比里
有一半回退到 `L5c`,把配比扭曲成 `L5c 42% / L5ra 8% / L5rd 25% / L5sq 25%`,
**无法归因** —— 所以最终把它从 mix 里去掉。

**顺带修掉一个训练崩溃隐患:** `sample_episode` 的 `RuntimeError` 会穿透
`ProcessPoolExecutor.ex.map`,**整个训练直接挂掉**。已在 `road_train.run_episode`
里加 `L5c` 回退(它是长期在用的主训练级,已证 20/20 可通)。

**这解释了为什么之前"多跑几条赛道"没有带来多样性的收益** —— 赛道是同构的,
只是参数抖动。形状空间打开之后,泛化才第一次成为可测的东西。

### 3.2 schema:`spica_v3`

沿用 v1 的自描述哲学,但多编一个字段 —— v2 的 `action_to_speed` 依赖 `V_LO/V_HI`,
光有 scale 不足以还原模型行为。

```
spica_v3                      scale 1.5, V ∈ [0.45, 1.0]   ← 与当前的 road_v2 逐位等价
spica_v3_s3_v0.45-3.0         scale 3.0, V ∈ [0.45, 3.0]
```

- **无后缀 = 当前的 road_v2**:观测公式、`V_LO/V_HI`、网络结构全同。这样
  `candidate_167` / `candidate_136` 不改名就能被 spica 代码加载。
- `_sN` 与 v1 同义:**训练时**速度通道的归一化尺度,不是部署速度
  (`reference_schema_suffix_is_not_speed` 的坑同样成立)。
- `_vA-B` 是动作速度范围,决定 `action_to_speed`。

`RoadPolicy` 接受 `road_v2` 与 `spica_v3` 两种前缀。`common/policy_portfolio.py`
的档位表加 spica 列,`select()` 逻辑不变(仍是最近档选择,不插值)。

### 3.3 速度:现在**不**解锁,这是有意的

v2 当前的天花板是硬编码的,实测确认了:

```
V_LO, V_HI = 0.45, 1.0   -> 动作空间能表达的最高目标速度 = 1.000 m/s
candidate_167 速度输出实测: 中位 0.499 m/s, 最大 1.000 m/s, 2.9% 饱和在 +1.0
```

还有两处也在压:
- `road_env.py`: `v_top = rng.uniform(0.85, 1.1)`,`cap = rng.uniform(V_LO, V_HI)`
- `road_teacher.py`: `v_top = min(pl.cap, pl.v_top)`

**但 spica 第一步不去动它。** 理由:v1 已经在 1.0/1.2 上有模型,而它们**在复杂赛道上
是 0.400**。在策略还没学会走之前先让它跑,只会让失败更难归因。
先把复杂度这关过了,速度是后面独立的一步(见第六节)。

## 四、训练方案

### 4.1 第一步:解锁几何(唯一必要的改动)

在 main 的 `road_train.py` 上,把 v1 模型灌进来当初始化,在复杂赛道上继续 DAgger。

**已落地为 `common/spica.py`**(不是伪代码),`load_init(path)` 对 v1 自动重排、
对 road_v2/spica 原样读。核心就是这段:

```python
def remap_v1_to_spica(path):
    """v1(52维) -> spica(53维)。每帧 52 列插到 53 列块的前 52 位,新通道权重置 0。"""
    with np.load(path) as z:
        w0 = np.zeros((256, v2.DIM * v2.FRAMES), np.float32)      # 265
        for j in range(v2.FRAMES):
            w0[:, j*v2.DIM : j*v2.DIM+52] = z['w0'][:, j*52 : j*52+52]
        w2 = np.zeros((2, 256), np.float32)
        w2[0] = z['w2'][0]                                        # 转向行原样搬
        b2 = np.array([z['b2'][0], 0.0], np.float32)              # 速度行置 0
        return dict(schema=np.array(SCHEMA), w0=w0, w1=z['w1'].copy(), w2=w2,
                    b0=z['b0'].copy(), b1=z['b1'].copy(), b2=b2)
```

改的两处闸:
1. `road_train.py` 的 `--init`:改用 `common.spica.load_init`,接受
   `low_speed_steering_v1*` 并自动重排。
2. `common/road_policy.py` 的 `RoadPolicy.__init__`:接受 `road_v2` 与 `spica_v3` 两种前缀。

**端到端冒烟测试已通过**(`candidate_002` = m4):
```
1. L5c 已注册        LEVELS 末尾
2. L5c 生成闭环       10/10
3. load_init 重排     w0 (256,265)  w2 (2,256)  b2 [0.0304, 0.0]
4. 重排无损           前 52 维逐位相同;转向输出最大差 0.000e+00
5. 速度通道初值       输出 0.0 -> action_to_speed = 0.7250 m/s
```

**速度通道的初值(实测,不是推断):** 速度行权重置 0 后网络速度输出恒为 **0.0**,
而 `action_to_speed(0.0) = 0.725 m/s` —— **是区间中点,不是下限 0.45**。
所以重排后的模型起步速度是 0.725 m/s,比 m4 的训练速度 1.0 略慢、比 0.45 快得多。
这个起点是合理的,不是"以最低速起步"。

### 4.2 训练配置 —— 闭环赛道为主

**设计约束:闭环前提下整复杂赛道,但别太复杂。**
所以不再从 L3(开放路段)往上推 L4/L5/L6,而是直接在新的闭环级别上练。

已落地(§3.1e 配置 C):

```python
# simulation/fastsim/road.py 的 LEVELS 里加(在末尾,不动已有下标)
Level('L5c', loop=True, loop_bend=(0.9, 1.2)),
```

R_min 中位 0.916、92% 的赛道探到 v1 地板 1.0 以下、28% 低于车极限、老师 25/25 出圈(§3.1e)。

**实际启动的命令(2026-09-28 已跑):**

```sh
python -m training.road_train --out runs/spica_a \
    --init models/steering_v1/candidate_002.npz \
    --start-level L5c --mix 'L5c:0.6,L5:0.4' --eval-levels L5c,L5 \
    --rounds 40 --episodes-per-round 240 --updates 3000 --eval-count 200 \
    --workers 12 --torch-threads 12 --ema 0.999
```

- **`--mix 'L5c:0.6,L5:0.4'`** 而不是 `--start-level L5c` 单级:
  按几何难度自动升级的课程(`promoted`)在这里**不适用** —— 它会按 `LEVELS` 的
  下标往上走,而 `L5c` 加在末尾,升不上去。用固定配比:
  **60% 在更紧的 L5c 上学新几何,40% 留在 L5 上保住已会的**。
- **`--eval-levels L5c,L5`**:每轮**分级报**,能直接看出「新几何在学」和
  「旧几何没退化」这两件事有没有同时成立。只看总平均会互相稀释。
- **`--start-level L5c` 直接上是可以的(已实测)**。方案初稿担心
  「m4 在 L5c 上可能一开始完全不能跑,beta 曲线前几轮就掉到 0」——
  **冒烟测试推翻了它**:重排后的 m4 在 L5c 上第一轮就有 **0.150** 出圈率,
  不是 0。所以不需要先用 L5 过渡。
- **为什么不用开放路段 L3/L4**:它们的失败轴里混了"边界信息缺失"
  (`gap_chance`/`one_side_none`),而真实赛道**双边都有锥桶**。在闭环上练,
  难度干净地来自几何。
- **`--ema 0.999`**:`road_train.py` 的注释记了单存档在方角上忽好忽坏。
- **`--workers 12`**:共享服务器,队友在 WORKER_BASE 0(域 43-50),
  另一组 20(域 63-70)。12 进程不影响 Win 侧(训练是纯 CPU 的 fastsim,不开 Gazebo)。

### 4.3 对照臂(把"架构收益"和"训练量"分开)

三臂,同种子同轮数:

| 臂 | 初始化 | 目的 |
|---|---|---|
| A | 随机 | 当前的 v2 基线,复现 `candidate_167` |
| B | **m4 重排** | v1 的知识能不能迁移到闭环复杂赛道 |
| C | `candidate_167` 热启动 | 纯"更多训练量"的对照 |

**A vs B 是架构问题,B vs C 是数据问题。** 只有三臂都有,B 的收益才能归因。

### 4.4 评估

- **主仪器**:`evaluation/road_eval.py`(FastSim,无 guard),种子基 90M。
  报**每级分开**的干净率,不要报总平均 —— 会稀释掉难点级别的差异。
  **`L5c` 必须单独报**,它是"和真实赛道同构"的那一级。
- **次仪器**:`evaluation/road_track.py` + `simulation/gazebo/`(含 guard=0.25)。
- **A–D 只做最终验证**,不进训练、不挑模型(`project_goal_clean_lap_on_ad`)。
- **报数字必须说清哪个仪器**(`project_two_evaluation_instruments`)。这次纠正
  v1 记录的教训就是这条。

## 六、第二步:速度解锁(**2026-09-29 已落地**)

原文写「等复杂赛道的干净率追平 v2 之后再动」,后来实测发现**不动它才是错的** ——
速度不是"更快的档位",是**动作空间本身**,它同时压着老师标签和学生输出。
下面两道闸都是 2026-09-28 实测出来的。

### 6.1 第一道闸:动作编码 `V_LO/V_HI = 0.45/1.0`

`action_to_speed` 的区间就是"策略物理上能表达的最高目标速度"。实测:

```
      老师想跑  speed_to_action       再解回来
      1.00           1.0000     1.0000
      1.20           1.0000     1.0000  <-- 被削掉
      3.00           1.0000     1.0000  <-- 被削掉
```

老师自己的速度规划 p10 0.62 / 中位 1.01 / p90 2.63 / 最大 3.00 m/s,**50.5% 超过 1.0**。
**这就是「cap 从 1.0 提到 3.0,老师成绩一字不变」的原因。**

把编码放开到 `V_HI=3.0`(只改编解码,不改网络),老师仍然 100% 出圈:

```
   cap       出圈       均速      最高速     >1.0占比
  1.00    1.000    0.807    1.000       0.0%
  1.50    1.000    0.906    1.500      36.6%
  3.00    1.000    0.936    2.821      33.5%
```

### 6.2 第二道闸:老师的 `A_LAT`(比车物理保守 26 倍)

车物理抓地 `a_lat_max = 7.85 m/s²`(0.8g,`common/params.py`)。老师的 `A_LAT = 0.30`
意味着 R=1m 的弯它只规划到 `sqrt(0.30) = 0.55 m/s` —— **标签本身就从不要求快**。
`V_HI=3.0` 下扫 `A_LAT`:

```
   A_LAT       出圈       均速      最高速        均圈时
    0.30    1.000    0.936    2.821      30.97   ← 改前
    0.80    1.000    1.267    2.971      22.95
    1.50    1.000    1.539    3.000      18.97
    2.50    1.000    1.789    3.000      16.30
    4.00    1.000    1.976    3.000      14.39
    6.00    1.000    2.109    3.000      13.40   ← 改后(物理的 76%)
```

**A_LAT 从 0.30 提到 6.0,均圈时 30.97s → 13.40s(2.3 倍),仍然 100% 出圈。**

**但 6.0 不是默认值,是显式参数。** 模块默认仍是 0.30:`A_LAT` 只有在 `v_hi` 明显大于 1
时才有区别 —— `v_hi=1.0` 的默认契约下 `sqrt(6R) >= 1.0` 只要 `R >= 0.17m`,任何弯都不减速,
等于把 09-26 修掉的"满速冲进弯"放回来。所以放开速度时**必须连 `--a-lat` 一起传**:
`road_train --speed-scale 3.0 --v-hi 3.0 --a-lat 6.0`。评估要复现同一批局,也得传同一个值
(`road_eval` 不走三层检查所以无关;`eval_speed` / `goal_check` / `road_track` 有 `--a-lat`)。

### 6.3 落地方式:schema 自描述,不改历史模型

`common/road_policy.py` 现在把 (scale, v_lo, v_hi) 编进 schema 后缀:

```
road_v2 / spica_v3              scale 1.5, V ∈ [0.45, 1.0]   ← 与当前版本逐位等价
spica_v3_s3_v0.45-3             scale 3.0, V ∈ [0.45, 3.0]
```

`spec_of(schema)` 反解,`suffix_of(enc)` 生成。**默认契约返回空后缀**,
所以历史模型不改名、不改码、逐位不变(已用 `action_to_speed` / `observe` 逐位对比验证)。

### 6.4 还没做的

1. **`HORIZON` 仍是 8.0。** 原文担心的"窗口锁死 2.74 m/s"在 `A_LAT=6.0` 下**不成立了**
   (限速项从 `sqrt(0.30·0.95)=0.534` 变成 `sqrt(6.0·0.95)=2.39`),
   但 3.0 的刹车距离 `3.0²/(2·0.45) = 10.0m` 仍超过 8m 窗口。

3. **闭环干扰(风险 7)在高速度下未复测。** 1.0 以内靠 48 扇区隐式处理够用,

   但 0.150 是起点不是终点 —— 40 轮能不能爬到可用水平,是 `runs/spica_a` 要回答的。
2. **曲率地板和边界缺失是两个轴。** 开放路段 L4 比 L3 多的是
   `gap_chance`/`one_side_none_chance`,L3→L4 干净率从 0.625 掉到 0.400。
   **改练闭环之后这个轴自动消失了**(真实赛道双边都有锥桶),这是好事 ——
   但代价是 spica 从此不覆盖"单侧无边界"的场景。**若实车场地有胶带段,
   需要单独保留一个评估级。**
3. ~~老师自己会不会在复杂赛道上失手?~~ → **已做,老师 L1–L6 全部 40/40**
   (§1.6)。标签存在,方案的前提成立。但 **L5 的重规划失败 1235 次**是新的疑点:
   平均每局 31 次标签来自"过期的规划",这部分标签质量没被验证过。
4. ~~v1 在 L1/L2 上的表现没有重测~~ → **已做,前提成立**:L1 1.000、L2 0.925。
   车辆参数与观测口径都没变,塌陷确实从 L3 开始。
5. ~~L4/L5/L6 的干净率精确都是 0.400,这个巧合要查~~ → **已查,不是同一批种子**。
   三级重叠 3 条 vs 独立期望 2.56 条,并集 34/40。n=40 站得住。
6. **L5 是闭环赛道,和开放路段的环境动态不同。** `generate_loop` 的注释明说:
   车在任何位置都能看到折回来的其它路段的锥桶,这正是把 v2 在赛道 A 上干扰掉的
   东西。L5 上 m4 的塌陷里有多少是"闭环干扰"、多少是"曲率地板",没有分离。
   **改练闭环之后这个问题从"风险"变成"必须解决的核心问题"** —— 见风险 7。
7. **「检测到弯」在闭环上是歧义的(新,§3.1d 引出)。** 10m 外雷达看到的锥桶
   同时包含折回来的其它路段。策略要"看到弯就降档",就必须区分
   **"前方本路的弯"和"旁边别的路段"**。当前策略靠 48 扇区 + 5 帧历史隐式处理,
   在 1.0 m/s 以内够用(速度低、来得及),**但解锁速度后这是第一个会崩的地方** ——
   高速下认错弯 = 在直道上无谓刹车,或该刹没刹。
   **建议:在 §六 解锁速度之前,先做一个"闭环干扰"专项评估。**
8. ~~`L5c` 低于车极限的赛道太多、过不去?~~ → **已排除,而且配置已调温和。**
   原方案 F 有 80% 赛道低于车极限,老师在它上面 **30/30 出圈**、净空 p10 +0.134,
   最紧一条 R_min=0.638 照样干净通过 —— **"低于车极限"不等于"过不去"**
   (0.83 是中心线静态判据,老师走外-内-外,实际半径更大)。
   **但「别太复杂」这条约束在,所以最终定的是更温和的配置 C(28% 低于车极限)。**
9. **闭环干扰的量化(新)。** 风险 6 说的"折回来的其它路段干扰",在 L5/L5c 上
   没有分离过。**这是 spica 唯一一个"训练分布本身"的未决问题**:
   如果 L5c 上 m4 的塌陷里干扰占大头,那 spica 学到的一部分是"在杂乱雷达里找本路",
   这在真实赛道(也有折回的赛段)上**可能是对的**,也可能过拟合到闭环的特定折法。
   **判据**:对比同一批几何在闭环(L5c)和开放(L5 去掉 loop)上的干净率 ——
   开放版没有折回路段。这个对照还没做。

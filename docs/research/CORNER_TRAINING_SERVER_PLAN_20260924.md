# 转角问题：租机与训练准备（2026-09-24）

## 当前决定

先保留现有 `candidate_060.npz` 作基线，不立即从零训练。先定位转角失效来自观测、转向执行、教师还是赛道分布，再决定是否续训或重训。实车速度闭环与转向策略分开评估。

现有图片只给 CPU / 内存，没有价格、磁盘、独占性和 GPU。按目前 `fastsim.low_speed_train` 的 CPU 小网络和串行仿真采样，优先询价 **9950X / 16 核 / 64 GB**。14900K / 64 GB 可作同价位备选。128/192/256 GB 和双路机器目前没有已证明的收益；若未来改成多进程采样或并行 Gazebo，再用计时结果决定扩容。租用前确认 Ubuntu 22.04、NVMe 至少 200 GB、SSH、可安装依赖、是否独占 CPU、实际计费单位和关机计费规则。不要仅凭“24 核”推断比 16 核更快：14900K 为 8 个性能核 + 16 个能效核。

## 先做的诊断

1. 固定当前模型 SHA256、代码提交、目标速度、车端配置。记录转角失败的左右方向、位置、雷达帧、策略动作、实际舵机命令、编码器速度和 IMU 偏航角速度。至少区分“策略晚打方向”和“打了方向但车没转”。
2. 车端 `wheelbase=0.33 m` 已统一；`max_steer=0.55 rad` 和 `steer_rate=4.0 rad/s` 仍是假设。量左右满舵角和从中位到满舵的时间，再改仿真。检查雷达扇区方向、安装偏角、锥桶和墙壁是否被看见。以 0.7 m/s 限速评估，不能用直线 PID 好坏代替转角表现。
3. 固定同一组单弯、S 弯、长 180° 弯和无锥桶缺口，在 FastSim、Gazebo、实车逐一重放。分别记录成功率、最小净空、开始打方向的位置、转向响应延迟和速度。旧策略在 FastSim 与 Gazebo 的小样本排序不一致，FastSim 只能作筛选；Gazebo 和实车是后续门槛。
4. 先确认教师控制器在这些弯上能过。如果教师也失败，先修几何、预瞄或可观测性；不要把失败教师输出当训练标签。雷达看不到地面胶带，缺口若需视觉/定位，单靠增加训练步数无法补出这个信息。

## 训练分支的选择

| 诊断结果 | 下一步 |
|---|---|
| 指令及时、实车转向不足 | 优先校准舵角、转向速率与 Gazebo/车端控制映射；暂不重训 |
| 教师能过，学生在新弯型/间距失败 | 保留网络架构，加入这些场景，从现有权重初始化，清空旧分布 replay，重新采集 DAgger 数据 |
| 教师在缺口也不能过 | 增加可用观测或路线先验，先让教师过，再训练学生 |
| 校准后旧权重热启动持续劣于随机初始化 | 再做从零训练对照，使用完全相同的训练预算和独立评估集 |

## 租机前与上机后的验收

- 仓库中只有 `runs/low_speed_a/candidate_060.npz` 等导出权重，**没有**完整 `latest.pt`。现有 `--resume` 依赖 `latest.pt`，现有 `--init` 只支持 Phase B；需先实现从 `.npz` 初始化到新目录、旧 replay 不继承，并保存新的完整断点。
- 新训练目录保留基线权重、配置、Git SHA、随机种子、原始逐局结果及 SHA256。训练、模型选择、最终测试的种子分开；不要继续把训练时用于挑模型的前 50 个种子算作独立测试。
- 先在租机上用 10 万环境步做流水线计时，分别记录仿真采样、网络更新、评估、Gazebo 单局耗时和内存峰值；再决定并行进程数与租期。当前训练入口设 `torch.set_num_threads(2)`，环境 episode 在主进程串行跑；64/96 核不会自动加速这一段。
- 在同种子、同速度、同赛道上对比旧模型、热启动模型、从零模型；报告每种弯型的逐局失败与置信区间。小样本 `clean` 不能替代完整验证。
- 服务器不存车的 WiFi 密码、SSH 私钥或实车 ROS 域凭据。仿真保持与车不同的 `ROS_DOMAIN_ID`。训练输出先本地备份再释放实例。

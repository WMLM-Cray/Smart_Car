# Gazebo 最小验证工程

保留两个 ROS 包：racecar_sim（车模、控制器、传感器、接线与启动）和 racecar_test_assets（红蓝锥桶模型与环境钩子）。
从历史提交 0ed23c4 恢复，未恢复导航、旧策略训练器、历史截图或批量实验。

## 构建与启动

在安装 ROS 2 Humble 与 Gazebo Classic 的 Ubuntu 环境，从仓库根目录执行：

```sh
source /opt/ros/humble/setup.bash
cd simulation/gazebo
rosdep install --from-paths src --ignore-src -r -y
colcon build --symlink-install
bash run_sim.sh use_gui:=false
```

run_sim.sh 的仿真域取环境变量 ROS_DOMAIN_ID,默认 60,拒绝实车域 42;共享服务器上 43–50、84 已被别人的仿真占用,不要用。只启动仿真，不自动使能策略，也不清理其他进程。
默认 racecar.world 是空场。历史 trackA.world 是旧版冻结赛道，不能当作当前根目录 maps/A–D 的同一评测集。

## 接口与验证边界

/cmd_vel 使用 m/s 与偏航角速度 rad/s；绝不能发送实车 PWM。
已恢复 /scan、IMU、里程计与 TF 接线所需工程。轴距 0.33 m，雷达 1667 点、12 Hz。
Gazebo max_steer_angle=0.55 是左右车轮关节限位，不能直接等同 FastSim 的等效自行车角 0.379；仍需验证控制器到实际转弯半径。
Gazebo 速度控制没有复现 ESC 起转平台与真实 SpeedLoop，当前只恢复工程，不宣称完成 sim-to-real 对齐。

本轮在 Windows 做语法、XML/YAML、依赖路径与资源引用检查；ROS 构建和 Gazebo 动态运行待 Ubuntu 环境验收。

## sim_reset.py —— 重跑一圈（别用 Gazebo 菜单的复位）

```sh
python3 simulation/gazebo/sim_reset.py                  # 回原点（A–D 的起点）
python3 simulation/gazebo/sim_reset.py --x 11.0 --y 0.75   # 旧 trackA.world
```

**别用 Gazebo 菜单里的复位。** 三条路只有传送这条能用：

| 做法 | 能搬动车 | 之后还能跑 |
|---|---|---|
| Edit→Reset Model Poses（Ctrl+Shift+R）= `/reset_world` | ✗ | — |
| Edit→Reset World（Ctrl+R）= `/reset_simulation` | ✓ | **✗ 再也跑不了** |
| 本脚本 = `/set_entity_state` 传送 | ✓ | ✓ |

`/reset_world` 对这辆车没用——车是运行时 `spawn_entity` 进来的，不在 world 文件里，
它只复位 world 里原有的模型。`/reset_simulation` 更糟：它把仿真时间倒回 0，
`gazebo_ros2_control` 从此不再注册 update 回调，Gazebo 照常步进（RTF 0.96、`/scan`
9.6 Hz）但 `/joint_states` 掉到 0 Hz，切换控制器报 `Switch controller timed out
after 5s`，而 `list_controllers` 仍显示 active 是假象，只能重启整个 launch。

光传送也不够：策略的叠帧缓冲里还压着撞车那几帧，接着跑等于拿撞车时的历史开车。
所以顺序是**停策略（触发 `policy.reset()` 清缓冲）→ 传送 → 再使能**，脚本按这个顺序做。

另注：启动这套栈时仿真不能是暂停的。控制器若在暂停状态下 configure+activate，
硬件接口接不上，之后解暂停也没用（现象同上），同样只能重启。

坐标默认是原点——`official_to_gazebo.py` 生成的 A–D 已经把起点归零（spawn 硬编码在
(0,0,0)），所以不带参数就是对的。旧版 `trackA.world` 起点在 (11.0, 0.75)，要显式给。
域必须和 `run_sim.sh` 一致（默认 60），否则脚本对着一个空图说话，什么都没传送却不报错。

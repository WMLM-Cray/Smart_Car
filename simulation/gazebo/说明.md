# Gazebo 最小验证工程

保留两个 ROS 包：racecar_sim（车模、控制器、传感器、接线与启动）和 racecar_test_assets（红蓝锥桶模型与环境钩子）。
从历史提交 0ed23c4 恢复，未恢复导航、旧策略训练器、历史截图或批量实验。

## 构建与启动

在安装 ROS 2 Humble 与 Gazebo Classic 的 Ubuntu 环境，从仓库根目录执行：

```sh
source /opt/ros/humble/setup.bash
cd simulation/gazebo
rosdep install --from-paths src --ignore-src -r -y
colcon build --symlink-install
bash run_sim.sh use_gui:=false
```

run_sim.sh 的仿真域取环境变量 ROS_DOMAIN_ID,默认 60,拒绝实车域 42;共享服务器上 43–50、84 已被别人的仿真占用,不要用。只启动仿真，不自动使能策略，也不清理其他进程。
默认 racecar.world 是空场。历史 trackA.world 是旧版冻结赛道，不能当作当前根目录 maps/A–D 的同一评测集。

## 接口与验证边界

/cmd_vel 使用 m/s 与偏航角速度 rad/s；绝不能发送实车 PWM。
已恢复 /scan、IMU、里程计与 TF 接线所需工程。轴距 0.33 m，雷达 1667 点、12 Hz。
Gazebo max_steer_angle=0.55 是左右车轮关节限位，不能直接等同 FastSim 的等效自行车角 0.379；仍需验证控制器到实际转弯半径。
Gazebo 速度控制没有复现 ESC 起转平台与真实 SpeedLoop，当前只恢复工程，不宣称完成 sim-to-real 对齐。

本轮在 Windows 做语法、XML/YAML、依赖路径与资源引用检查；ROS 构建和 Gazebo 动态运行待 Ubuntu 环境验收。

## 单赛道验收（run_road_policy_once.sh）

一次跑完「起仿真 → 起策略 → 打分」：

```sh
bash simulation/gazebo/run_road_policy_once.sh <world源> <模型> <layout> <输出.json>
```

`world源` 必须带 `gazebo_ros_state` 插件，否则 `/model_states` 拿不到，脚本会先拒绝。
`layout` 由 `official_to_gazebo.py` 生成（见下），`输出.json` 是 `track_eval.py` 的判据结果。

用环境变量控制：`WORKER`（并行槽位）、`POLICY_SPEED`、`GUARD`、`RUN_SECONDS`。

**两个脚本的环境变量不通用**，因为 v1/v2 节点的命令行本身不通用：

| | `run_s3_policy_once.sh`（v1） | `run_road_policy_once.sh`（v2） |
|---|---|---|
| 速度 | `POLICY_SPEED` → `--speed`，固定油门 | `POLICY_SPEED` → `--speed-cap`，**上限**（策略自选 0.45~1.0） |
| 防撞 | `GUARD` → `--guard`，默认实车 0.25 | **没有防撞**，设了 `GUARD` 直接 `exit 5` |
| 雷达超时 | **不认** `--scan-timeout`，设了 `SCAN_TIMEOUT` 直接 `exit 5` | 同左（选项名是 `--sensor-timeout`，未接出来） |

v2 这条路上没有 `ScanGuard`（带 guard 的是队友分支上的实车节点 `road_car_node.py`，
尚未合并），所以它的撞锥统计是**纯物理碰撞**，与我们惯用的 guard=0.25 口径不可比。
两个脚本都不静默吞掉传不进去的环境变量——宁可 `exit 5`，也不产出一批看着正常、
实则换了口径的数字。

> v2 节点的速度选项真名是 `--speed-cap`。写 `--speed` 也能跑通，但那是 argparse 的
> **前缀缩写**，节点哪天加一个 `--speed-xxx` 就会变成 `ambiguous option` 直接 exit 2。

退出码：`2` 用法/world 缺插件，`3` 端口被占（有残留 gzserver），`4` 本轮 gzserver
中途退出（JSON 不可信），`5` 传了节点不认的环境变量，`6` 策略节点已退出。
`5` 和 `6` 都是**在起 gzserver 之前或刚起完**就判死——策略节点是后台进程，它自己
校验参数失败时脚本看不见，会照跑满 120s 再产出一份 `laps: 0` 的完整 JSON，那份
JSON 和「模型跑不动」长得一模一样，是最容易被误当成模型缺陷的假信号。

这些约定由 `test_run_scripts.py` 钉住（只跑参数校验分支，不需要 ROS）。

**并行隔离的四样东西**（由 `WORKER` 决定，少一样就互相污染）：ROS 域、Gazebo 端口、
world 文件名、`/tmp` 控制器 yaml。第 4 项由 `sim_bringup.launch.py` 按 `ROS_DOMAIN_ID`
分文件——并行时多个 gzserver 会同时写同一个 `/tmp/racecar_ros2_control.yaml`，
读到写了一半的文件会让 controller_manager 起不来。

> ⚠️ **gzserver 不会随 `ros2 launch` 一起死。** `kill $SIM_PID` 只杀掉 launch 包装进程，
> gzserver/gzclient 被孤儿化后继续占着 `GAZEBO_MASTER_URI` 端口和 world 文件。
> 后果不是"多占一点内存"，而是**下一批的数据被污染**：下一批 cp 覆盖同一个 world 文件
> → 它的 gzserver bind 端口失败 → 车 spawn 进**残留的旧 gzserver** 的 world 里，
> 而 `track_eval.py` 拿新赛道 layout 去评分。产出的 JSON **完全像模像样**
> （`laps`/`cone_hits`/`off_track_samples` 都正常），没有任何数字提示你跑错了赛道。
>
> 实测：arc 批之后 narrow/right/s_bend 共 12 条跑的全是 arc 的赛道，同 worker 槽位的
> 三条轨迹相距 **0.007 m**（纯采样噪声）。
>
> 脚本的处理：`cleanup()` 按 **world 文件名** pkill（文件名含 worker 号，不会误杀同批
> 其他 worker，更不会碰别人域）；开跑前预检端口，被占则 `exit 3`；跑完复查本轮 gzserver
> 是否还活着，死了则 `exit 4` 并声明 JSON 不可信。
>
> **权威判据是 launch log 的 `world加载次数 / spawn次数 / 进程死亡数`，不是轨迹间距离**
> ——几何相近的赛道彼此中心线中位距离本来就小，车在 A 上跑也贴近 B。

## track_eval.py —— 判据与计时口径

判据全部来自 `/model_states`（`gazebo_ros_state` 插件），不依赖接触传感器——
生成的锥桶是静态 box，没装接触传感器，碰撞只能靠几何判。

* **撞锥** 车辆外接圆与锥桶 box 的水平距离 < 阈值。同一锥桶连续接触只算一次，离开 0.3 m 后才重新计。
* **出界** 到最近锥桶距离 > `OFF_TRACK = 1.60`（赛道半宽 0.75）。**对半宽 0.625 的窄道
  这相当于 2.6 倍半宽，会漏判**——窄道上请改用「横向偏移 / 该点半宽」口径。
* **圈数** 过起点线且方向正确。

**计时用仿真时间（`/clock`），不是墙钟。** 并行验收时 N 个 worker 抢 CPU，墙钟会被拖长，
同一策略在不同 worker 上的圈速就不可比；仿真时间是物理时间，与 CPU 负载无关。
QoS 必须 **BEST_EFFORT**——发布端是 `rclcpp::ClockQoS`（BEST_EFFORT/VOLATILE/depth1），
RELIABLE 订阅者和它不兼容，会**静默收不到**（不报错）。`/clock` 没起来时自动退回墙钟，
并在 `clock_source` 字段写明，不会静默算错。墙钟值仍保留在
`lap_splits_wall_s` / `elapsed_wall_s`，只是诊断用，不参与判据。

`--seconds` 是**仿真秒**；`--max-wall-factor` 给墙钟硬上限，防止 gzserver 卡死时 worker 永久挂着。

## official_to_gazebo.py —— A–D 官方赛道转 Gazebo

```sh
python3 simulation/gazebo/official_to_gazebo.py --out runs/gz_official
```

锥桶和起点**直接取自本仓库的 `evaluation.road_track.official(name, fill_v=True)`**，
不自己解析 maps/ 下的 CSV/JSON——fastsim 验收用的就是这一个函数，从它取才能保证
Gazebo 里的赛道与 fastsim 验收时**逐点一致**，差异只可能来自物理。

`fill_v=True` 必须跟着传：fastsim 验收用的是它（沿黄 V 边界按 0.5 m 补桶），
否则 Gazebo 里的赛道和验收的那条不是同一条。

**起点必须归零。** Gazebo 的 spawn 硬编码在 (0,0,0)，而 `official()` 返回的中心线
`centre[0]` 是 START 框中心（如赛道 A 在 x=11.2 处）。所以整体做「旋转 `-heading[0]`
+ 平移 `-centre[0]`」，起点落到原点、车头朝 +x，与 spawn 对上。
不做这一步的后果（2026-09-25 实测）：车生成在赛道中段随机位置，往往紧贴锥桶，
一启动就被 ScanGuard 判截停——**看起来像模型崩了，其实是坐标不匹配**。

## hold_enable.py —— 仿真里的心跳源

策略节点把 `/policy_enable` 当**心跳**，超过 `ENABLE_TIMEOUT`（0.3 s）没收到就回中位。
所以 `ros2 topic pub --once` 只能让车动一下。实车上由网页摇杆发（推着才发），
仿真里用这个脚本代替，20 Hz 持续发到 Ctrl+C，退出时补发一次 `false`（不靠超时，停得更干脆）。

```sh
python3 simulation/gazebo/hold_enable.py        # 一直发到 Ctrl+C
python3 simulation/gazebo/hold_enable.py 60     # 发 60 秒
```
